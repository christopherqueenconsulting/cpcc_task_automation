## 1. TL;DR

What changed for grading, in five bullets:

- **The reference solution is authoritative** (#414, #415). If you upload a solution, the model
  is told that what it does is required and nothing that matches it may be penalised. With no
  solution the rubric prompt is the same as master's (#414 body).
- **Each error type counts once**, and point bands in every rubric no longer overlap
  (#400 before rc1; #416 in rc1). Scores near a band edge can move.
- **Grading runs as a background job** with a live table, Cancel, Retry failed and "Use another
  model" (#430, rc3). On Streamlit Community Cloud results are no longer saved on the server.
- **Requirements can be checked against the solution** (#432) and a requirement error that
  duplicates a model error is now noted, and can be dropped (#437). Both ship in rc4. The
  drop is off by default.
- **Reasoning effort is chosen per run** (#425, rc2), and Setup can recommend one (#428,
  rc4, apply by hand only).

## 6. Harness findings

These affect the evaluation CI, not grading.

1. **A new suite poisons the fast path (#433).** The base capture ran one subprocess for all
   suites. A suite the base did not know made it exit non-zero, the base became empty, and
   every suite read "capture formats differ" and ran paid. Seen on #428, #429, #432. Fixed per
   suite in #433 (`6321194`). Until the fix reached master, new-suite pull requests paid the full run.
2. **The per-process fence key made `test-case-generation` never identical-skippable
   (#439).** Master's fence key was random per process, so two captures differed in 12 of 12
   cases, verified master against master. #428's A/B run
   [40055768563](https://github.com/christopherqueenconsulting/cpcc_task_automation/actions/runs/40055768563)
   failed on this noise. Lesson: any new nonce must be pinned in the request capture or its
   suite cannot be skipped.
3. **The `detect` job fast path trusts a head capture for `claude/*`, `auto/*` and
   untrusted-author pull requests** (#433 body). Those have no paid `ab` job. A hostile capture
   equal to the base's gives a green status without a paid run. This predates #433. Off
   switch: the repository variable `PROMPT_EVAL_FAST_PATH=off`. Open for your decision; no
   change was made.
4. **A pull request run cannot switch the skip off.** `PROMPT_EVAL_FAST_PATH=off` does not
   reach the `ab` job's skip; only a workflow edit (Tier 2) or reverting #433 does. A
   maintainer dispatch with `full_ab: true` always runs the full paid A/B (#433 body).
5. **`ab-base-rule` has no `setup-java` step.** `ab`, `record` and `dispatch` in
   `.github/workflows/prompt-eval.yml` have one; `ab-base-rule` does not (read from the
   workflow file on `origin/master`). Effect on a Java-dependent suite: not verified.
6. **`dry_run` is ignored in `ab` mode.** The workflow always spends (#428, #429 bodies). When
   only new suites are affected, pass `suites=` explicitly to cap spend; the dispatch `suites`
   input is unioned with the pull request's own detection and never narrows.
7. **The A/B runs the pull request branch's own prompt-ab code.** A branch that predates a
   harness fix runs the old serial code; #422's first A/B took 66 minutes for that reason.
8. **Adaptive concurrency (#436).** Reference run
   [40033879399](https://github.com/christopherqueenconsulting/cpcc_task_automation/actions/runs/40033879399):
   four suites, 12 in flight, 657.4 s wall clock (grading 439.7 s, levelband 63.9 s,
   requirement-extraction 106.8 s, one more 45.3 s per #436, from artifact 12536757139), 33
   rate-limit warnings on the judge model and 9 judge fallbacks. After #436 the next A/B
   reports wall clock and 429 counts. Compare only grading, grading-levelband and
   requirement-extraction; `grading-solution` now has about twice the calls.
9. **GitGuardian Scan** reported a finding on commit `924db06` in #428 (history only, not
   required). A squash merge removes it from the branch.
10. **Codecov patch statuses** read low before the unit coverage upload. They are not required checks.

**Christopher only (Tier 2).** Only you force-push `release` ([RELEASING.md](RELEASING.md),

| From | To | Check first | Command |
|---|---|---|---|
| rc4 | rc3 | `git ls-remote --tags origin 'v0.2.0-rc3^{}'` must show `cff025a0745022bf4156625f87cab4ba3ba5cf67` | `git push --force origin v0.2.0-rc3:refs/heads/release` |
| rc3 | rc2 | `git ls-remote --tags origin 'v0.2.0-rc2^{}'` must show `4e647da5bcfafbf77d01dc9a4e930094d5d849fc` | `git push --force origin v0.2.0-rc2:refs/heads/release` |

The tags are annotated. If git refuses with a non-commit object error, push the commit
instead, for example `git push --force origin 'v0.2.0-rc3^{commit}:refs/heads/release'`. That
refusal was not observed here (not verified); the commands above are the form in RELEASING.md.

Then, in the same order as RELEASING.md "Roll back":

1. Fix forward on `master`: a revert pull request for the bad change, with a version bump and
   a CHANGELOG entry in the same PR, so new grades are not stamped with the bad version.
2. Mark the bad release: `gh release edit <bad-tag> --prerelease --notes "Rolled back in <new-tag>: <reason>"`,
   keeping its generated notes (the full command with `$(gh release view ... --json body -q .body)`
   is in RELEASING.md).
3. Saved runs keep their old scores. The run key has no code version, so after a code
   rollback the same inputs show the old result. Use "Re-grade this student" or delete the
   run's `<run_key>.json` to re-grade.
4. Prompt, rubric and model changes change the key, so those re-grade on their own. A model
   rollback needs no code rollback: run `model-rollback.yml` or set `CQC_MODEL_GRADING=<previous model>`.
5. To switch off one feature instead of a whole release: `CQC_GRADING_JOB=off` (#430),
   `CQC_REQUIREMENT_OVERLAP=notes` or `off` (#437), `CQC_EXECUTION=off` (#429, #424).
